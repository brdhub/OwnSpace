# 结构化简历条目仓库重构设计

## 目标

重建简历模块的结构化条目合同，删除“完成度”，以项目经历、实习经历、教育背景、专业技能、荣誉认证五类条目替代旧的通用结构。旧正式条目、AI 候选和依赖旧条目的 JD 匹配历史可以清空，PDF 原件保留，用户随后重新生成和导入。

## 方案选择

采用现有单表加判别式 JSON 内容的方案。`resume_entries` 继续保存公共的 `type`、`title`、`content_json`、`tags_json` 与时间字段；Zod 按 `type` 对 `content` 施加不同的严格字段合同。与在单表添加大量可空列相比，这能避免无意义空值；与每类单独建表相比，它保留了当前 AI 导入、去重和 JD 匹配的统一数据流。

## 类型与字段合同

- 项目经历 `project`：`title` 为项目名称；内容包含 `projectCategory`、`techStack`、`content`；标签独立保存，可由 AI 根据原文概括。
- 实习经历 `experience`：`title` 为公司或组织名称；内容包含 `position`、`techStack`、`responsibilities`、`workContent`；标签独立保存，可由 AI 概括。
- 教育背景 `education`：`title` 为学校名称；内容包含 `degree`、`major`、`dateRange`、`content`；标签独立保存。
- 专业技能 `skill`：`title` 为技能名称；内容包含 `proficiency` 与 `content`。`proficiency` 只能为“了解、熟悉、熟练、精通”；保存时标签强制同步为仅包含技能名称。
- 荣誉认证 `honor`：`title` 为荣誉或认证名称；内容仅包含 `award`，用于奖项、等级或认证结果；不保存额外标签。

技术栈在界面中按逗号或换行录入，在 JSON 中保存为去重后的字符串数组。所有文本会去除首尾空白并保持现有长度上限。

## 数据库迁移

新增 migration：先删除优化建议、优化素材、优化任务、简历版本、AI 候选和正式条目，再删除 `resume_entries.completeness`，并给 `resume_entry_candidates` 增加 `tags_json`。迁移不删除 `resume_assets`，因此已上传 PDF 仍可用于重新生成候选；其提取状态重置为 `idle`。

## 数据流与界面

手工添加或编辑时，表单根据类型显示对应字段。类型切换只改变当前表单中的可见字段；提交时服务端重新按类型组装并通过 Zod 校验。条目列表按类型分组，展示类型名称、标题和关键摘要。

AI 生成候选时，提示词要求返回五类严格结构以及 `tags`。候选解析、暂存、审核编辑和正式接收全程保留标签。专业技能在服务端最终接收时仍强制将标签同步到技能名称，避免依赖 AI 遵守规则。

JD 匹配和描述优化继续消费统一的标题、类型、内容与标签。条目快照移除完成度，旧快照随迁移清空。

## 错误处理与验证

字段缺失、额外字段、非法掌握程度、空标题和过长内容由 Zod 返回到表单。AI 返回不符合类型合同的数据时整批拒绝，不写入候选。测试覆盖五类条目、技能标签同步、AI 输出、数据库列和迁移清理语句；最后运行完整测试、类型检查、lint 与构建。
