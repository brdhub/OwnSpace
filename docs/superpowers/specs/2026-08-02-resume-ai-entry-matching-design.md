# 简历结构化条目提取与 JD 匹配设计

## 目标与范围

本轮在现有简历仓库基础上交付两项 AI 辅助能力：

1. 用户选择一份已成功提取文字的 PDF，主动调用 DeepSeek 生成结构化条目候选；候选经去重、编辑和用户确认后才进入正式条目仓库。
2. 用户粘贴并确认 JD 后，主动调用 DeepSeek，从现有正式条目中推荐适合该岗位的素材；用户可以增删选择并保存素材快照。

本轮不实现 PDF OCR、JD 图片 OCR、针对 JD 的描述改写、逐条改写建议、岗位简历版本、PDF/Word 导出或飞书同步。界面保留“优化条目描述”入口，但保持禁用并显示“后续开放”。

## 核心原则

- PDF 上传后只执行本地文字提取。只有用户点击“生成结构化条目”后，才把该 PDF 的提取文字发送给 DeepSeek。
- AI 只能整理输入中已有的事实，不得补写数字、职责、技能、结果或业务规模。
- 候选条目必须附带原文依据。无法确认的内容标记为待补充，不得猜测。
- AI 结果不能直接写入正式条目。用户必须先查看、编辑并确认。
- JD 推荐只做条目筛选和匹配理由说明，不修改原条目内容。
- API Key 仅从服务端 `.env.local` 读取，不进入 SQLite、客户端代码、日志或版本控制。

## 方案选择

采用“持久化候选 + 复用现有 JD 优化任务表”的方案。

未采用的方案：

- 浏览器临时保存候选：实现简单，但刷新或网络中断后结果丢失。
- 把候选塞入 PDF 记录的单个 JSON 字段：表结构少，但不利于单条编辑、状态管理和重复关联。

持久化候选能够在不污染正式条目仓库的前提下保留 AI 结果，并为去重、确认和重试提供清晰状态。

## 数据模型

### PDF 条目生成状态

在 `resume_assets` 增加：

- `entry_extraction_status`：`idle`、`processing`、`completed`、`failed`。
- `entry_extraction_error`：最近一次失败原因，可空。
- `entry_extracted_at`：最近一次成功生成候选的时间，可空。

这些字段与 PDF 文字提取状态分开，避免把“本地 PDF 解析”和“AI 条目生成”混为同一个状态。

### 结构化条目候选

新增 `resume_entry_candidates`：

- `id`
- `resume_asset_id`：来源 PDF，删除 PDF 时级联删除尚存候选。
- `type`：个人信息、教育经历、实习/工作、项目/科研、技能/证书。
- `title`
- `content_json`
- `source_excerpt`：支持候选事实的原文片段。
- `duplicate_entry_id`：疑似重复的正式条目，可空；正式条目删除时置空。
- `duplicate_kind`：`none`、`exact`、`similar`。
- `state`：`pending`、`accepted`、`ignored`。
- `created_at`、`updated_at`

所有结构变更通过 Drizzle schema 和 migration 完成。

### JD 推荐任务

复用现有：

- `resume_optimization_tasks` 保存岗位名称、已确认 JD、状态和经过校验的 AI 推荐结果。
- `resume_optimization_materials` 保存用户最终选择的条目快照。

本轮不写入 `resume_optimization_suggestions` 和 `resume_versions`。这些表留给后续描述优化与岗位版本功能。

## PDF 到结构化条目的数据流

1. 用户上传 PDF，系统在本地保存文件并提取文字。
2. 用户在已解析 PDF 上点击“生成结构化条目”。界面明确提示本次将发送该 PDF 的提取文字。
3. 服务端检查 API 配置、PDF 状态和提取文字，随后调用 DeepSeek。
4. DeepSeek 返回五类候选、结构化字段、原文依据和可能的语义重复提示。
5. 服务端使用 Zod 校验响应，并根据规范化标题与内容指纹执行本地完全重复检查。
6. 完全重复内容不新增候选；语义相似内容保存为候选并关联疑似正式条目。
7. 页面按类型展示待确认候选、原文依据和重复提示。
8. 用户可编辑、接受或忽略候选。
9. 接受时服务端再次检查正式条目仓库；通过后写入 `resume_entries`，并将候选标为 `accepted`。

重新生成候选不会覆盖已接受条目。待确认候选存在时，界面要求用户先处理或明确确认重新生成。

## 去重策略

去重分为两层：

1. 本地完全重复：对类型、规范化标题和稳定排序后的内容计算指纹。与正式条目完全一致时直接跳过，不依赖 AI。
2. 语义相似：DeepSeek 根据同类正式条目判断候选是否表达相同经历，并返回疑似条目 ID 与理由。系统只展示提示，不自动合并、覆盖或删除。

用户始终拥有最终决定权。确认候选时重新执行本地检查，避免并发操作产生重复正式条目。

## JD 匹配数据流

1. 用户进入“JD 匹配”，填写目标岗位并粘贴 JD 文本。
2. 用户点击“AI 推荐条目”。界面明确提示本次将发送已确认 JD 和当前正式结构化条目，不发送 PDF 原文或未确认候选。
3. DeepSeek 返回条目 ID、匹配等级（高、中、低）和基于 JD 的匹配理由。
4. 服务端验证所有返回 ID 均属于本次输入，并校验等级和理由格式。
5. 页面按匹配等级展示结果，默认勾选高匹配条目。
6. 用户可以增删选择并保存；系统为任务创建所选条目的不可变快照。
7. “优化条目描述”按钮保持禁用，显示“后续开放”。

推荐任务失败时保留岗位名称、JD 和已有选择，允许用户重试。

## DeepSeek 适配器

在 `src/features/resumes/` 内实现单一服务端 DeepSeek 适配器，并提供两个经过类型约束的入口：

- `generateEntryCandidates`：PDF 文字 → 条目候选。
- `recommendEntriesForJd`：JD + 正式条目 → 匹配推荐。

适配器使用 DeepSeek 的 OpenAI 兼容接口。基础 URL 和模型使用官方当前推荐值作为默认值，并允许通过 `DEEPSEEK_BASE_URL`、`DEEPSEEK_MODEL` 覆盖；`DEEPSEEK_API_KEY` 必填。实现前以 DeepSeek 官方文档核实当前端点、模型和结构化输出能力。

所有响应先解析 JSON，再经过 Zod 校验。调用方只接收校验后的领域对象，不直接处理供应商响应结构。

## 界面设计

简历页保留单一侧边栏入口，内部提供：

- `简历仓库`：PDF 原件、生成候选入口、候选审核区、正式条目仓库。
- `JD 匹配`：岗位名称、JD 文本、AI 推荐结果、手动选择和保存。

PDF 卡片仅在文字提取成功时启用“生成结构化条目”。处理中显示明确状态；失败时显示可重试错误。候选卡片展示类型、标题、可编辑内容、原文依据和重复提示。

JD 推荐结果以紧凑卡片展示匹配等级和理由。用户保存选择后仍可回看任务，但本轮不进入描述改写页面。

## 安全与隐私

- `.env*` 继续由 Git 忽略，仓库仅保留无密钥的 `.env.example`。
- 不在浏览器中读取或返回 API Key。
- 不记录 Authorization header、完整请求正文、完整 AI 原始响应或简历正文日志。
- PDF 条目生成只发送用户当前选择的 PDF 提取文字和去重所需的正式条目摘要。
- JD 推荐只发送已确认 JD 和正式结构化条目；不发送 PDF、未确认候选或其他模块数据。
- 所有外部调用必须由用户按钮操作触发，不增加后台任务或自动同步。

API Key 如果曾在任何可共享位置暴露，应先轮换，再只将新 Key 写入本机 `.env.local`。

## 错误处理

- API Key 缺失：不发请求，提示本地配置方法。
- 网络、超时或 DeepSeek HTTP 错误：保留页面输入和持久化状态，展示可重试提示。
- 非 JSON 或 Zod 校验失败：拒绝保存 AI 结果，记录不含敏感正文的可读错误。
- 返回不存在的条目 ID：整次 JD 推荐结果无效，不创建素材快照。
- PDF 没有文字层：不调用 DeepSeek，提示当前版本不支持 PDF OCR。
- 候选确认时发现完全重复：不新增正式条目，标记并提示已有条目。

## 测试与验收

自动测试覆盖：

- DeepSeek 配置缺失、默认配置和覆盖配置。
- 请求只包含允许发送的 PDF/JD/条目内容。
- 候选必须有类型、标题、结构化内容和原文依据。
- 无依据事实、非法类型、无效条目 ID、无效匹配等级和格式异常被拒绝。
- 本地完全重复、语义相似提示、确认时二次去重。
- 候选接受/忽略状态和正式条目写入。
- JD 推荐默认选择高匹配条目，并允许手动增删后保存快照。
- API 网络失败、HTTP 错误和格式错误的可重试状态。
- 数据库 migration 可在现有数据上安全执行。

最终验证命令：

```powershell
npm.cmd run db:migrate
npm.cmd test
npm.cmd run lint
npm.cmd run typecheck
npm.cmd run build
```

手动验收：

2. 使用另一份含相同经历的简历生成候选，验证完全重复不重复入库。
3. 粘贴 JD，生成 AI 推荐，手动增删条目并保存快照。
4. 验证“优化条目描述”入口可见但不可用。
5. 验证缺少 Key、网络失败和异常响应不会丢失用户输入或污染正式条目。
