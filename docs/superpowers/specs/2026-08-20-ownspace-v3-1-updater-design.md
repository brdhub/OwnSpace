# OwnSpace v3.1 自动与离线升级设计

## 目标

让已经安装过 OwnSpace 的 Windows 用户在启动时收到 GitHub 新版本提示，并能通过一次确认完成安全升级；同时提供不依赖在线检查的一键离线升级包。两种入口必须共用同一升级引擎，保留用户数据库、简历附件与本机密钥配置，并在失败时恢复旧版本。

v3.1 是首个内置升级器的版本。更早版本需要最后一次手动覆盖或运行 v3.1 离线升级包；从 v3.1 开始可以使用启动时在线升级。

## 非目标

- 不实现静默强制更新、后台定时更新或增量二进制补丁。
- 不引入 Electron、MSIX、Inno Setup、常驻 Windows 服务或新的 npm 依赖。
- 不自动创建 GitHub Release、不自动提交或推送代码。
- 不把数据库、简历附件、`.env.local`、Git 文件或构建缓存放入发布资源。
- 不支持从开发分支、预发布版本或任意第三方 URL 更新。

## 发布资源

每个正式 GitHub Release 使用语义化版本标签，例如 `v3.1.0`，并包含以下资源：

- `OwnSpace-v3.1.0-update.zip`：只包含受管理的程序文件。
- `OwnSpace-v3.1.0-update.sha256`：更新 ZIP 的 SHA-256。
- `OwnSpace-v3.1.0-manifest.json`：版本、文件名、SHA-256、最低升级器版本与发布时间。
- `OwnSpace-v3.1.0-offline-updater.zip`：包含更新 ZIP、manifest、校验文件及离线入口脚本。

manifest 采用固定结构：

```json
{
  "schemaVersion": 1,
  "version": "3.1.0",
  "minimumUpdaterVersion": "3.1.0",
  "archive": "OwnSpace-v3.1.0-update.zip",
  "sha256": "<64 lowercase hex characters>",
  "publishedAt": "<ISO 8601 timestamp>"
}
```

在线入口只读取固定仓库 `brdhub/OwnSpace` 的最新正式 Release，不接受用户输入仓库或下载地址。GitHub 检查失败、超时、限流或返回格式异常时记录简短提示并继续启动现有版本。

## 组件边界

### 启动入口

`start-ownspace.ps1` 仍负责启动编排，但把可测试逻辑拆到 PowerShell helper：

- 解析并比较语义化版本。
- 发现可用 Node.js/npm。
- 检查 GitHub 最新正式 Release。
- 调用升级引擎并处理“立即升级 / 本次跳过”。
- 在无更新、跳过或检查失败时继续原有迁移、构建和启动流程。

在线检查设置短超时，只在一次启动期间执行一次。更新提示必须显示当前版本、目标版本与“用户数据会先备份”的说明，不默认接受升级。

### 共用升级引擎

新增独立 PowerShell helper，接收以下已经验证的输入：

- 应用根目录；
- 本地 manifest 路径；
- 本地更新 ZIP 路径；
- 入口来源 `online` 或 `offline`。

升级引擎不了解 GitHub，也不自行选择文件。在线入口先下载到临时目录，离线入口直接解析包内资源，然后调用同一引擎。

### 发布打包器

现有分享脚本保留，用于完整首次安装包。新增发布脚本从 `package.json` 读取版本并一次生成三个发布文件和 manifest；受管理文件列表与当前分享包保持单一来源，避免在线包和离线包内容漂移。

## 数据与配置保留

当前版本继续使用应用根目录下的 `data`，v3.1 不在升级过程中迁移数据目录，以降低首个升级器对现有用户的风险。以下路径永远不属于受管理程序文件：

- `data/**`
- `.env.local`
- `backups/**`
- `node_modules/**`
- `.next-build/**`
- `.next-dev/**`
- `.git/**`
- 用户自行产生的日志

升级前先停止属于当前应用目录且占用 3000 端口的 OwnSpace 服务。服务停止后完整复制 `data`，包括可能存在的 SQLite WAL/SHM 文件和 `resume-assets`。如果存在 `.env.local`，一并复制到同一备份目录。

备份位置为 `backups/<timestamp>-v<current-version>/`，包含数据、配置、旧版受管理程序文件以及备份清单。默认保留最近三个成功升级备份；删除更早备份只在新版本健康检查成功后执行。任何清理不得跟随符号链接或超出 `backups` 目录。

## 升级状态机

升级过程按以下顺序执行：

1. 获取应用目录内的升级锁，拒绝并发升级。
2. 验证 manifest schema、目标版本、资源文件名与 SHA-256。
3. 检查 ZIP 条目，拒绝绝对路径、`..` 跳转、符号链接及受保护路径。
4. 解压到应用目录之外的临时目录，并验证必需文件完整。
5. 停止当前 OwnSpace 服务。
6. 创建完整升级前备份。
7. 替换受管理程序文件；保留数据、配置、依赖和缓存。
8. 当 lockfile 改变或依赖缺失时运行 `npm ci`。
9. 运行 `db:migrate` 与 `db:init`。
10. 运行生产构建并启动新版。
11. 轮询 `http://localhost:3000` 完成健康检查。
12. 成功后写入本地升级结果，释放升级锁并按保留策略清理旧备份。

任何一步失败都进入回滚：停止失败版本、恢复旧版受管理文件、恢复升级前 `data` 与 `.env.local`、按旧 lockfile 恢复依赖、重建并尝试启动旧版。回滚结果必须明确显示；如果旧版也无法启动，则保留所有备份并输出人工恢复路径，不继续覆盖文件。

数据库迁移可能不可逆，因此“恢复旧数据库”和“恢复旧程序”必须属于同一回滚事务边界。健康检查成功之前不得宣布升级完成。

## 在线更新流程

启动器通过 GitHub Releases API 请求固定仓库的最新正式 Release，忽略 draft 和 prerelease。仅当远端语义化版本严格大于 `package.json` 当前版本时提示。

用户选择立即升级后：

1. 从该 Release 的 assets 中按 manifest 声明的精确名称定位文件。
2. 将 manifest、ZIP 与校验文件下载到唯一临时目录。
3. 交叉核对 manifest SHA-256 与独立校验文件。
4. 调用共用升级引擎。

网络请求使用 HTTPS、固定 User-Agent、响应大小限制和超时；禁止自动跟随到非 GitHub 资产域之外的地址。在线更新是用户明确确认后的只读 GitHub 请求，需要在 `项目工程约束.md` 中登记为允许的外部调用例外。

## 离线更新流程

`OwnSpace-v3.1.0-offline-updater.zip` 解压后提供中文命名的 `.cmd` 入口。入口优先把包含 `start-ownspace.cmd` 和 `package.json` 的当前目录识别为旧版目录；识别不到时打开 Windows 文件夹选择器。

离线入口验证所选目录确实是 OwnSpace、读取当前版本、解析随包 manifest、校验内置 ZIP，然后调用共用升级引擎。目标版本不高于当前版本时默认拒绝；只有显式的开发参数才能覆盖，此参数不暴露给普通用户入口。

## Node.js 发现

移除启动器中指向开发者电脑的绝对路径。按以下顺序查找：

1. 应用目录可选的 `.runtime/node.exe` 与对应 npm；
2. `Get-Command node.exe` 和 `Get-Command npm.cmd`；
3. 常见系统 Node.js 安装目录。

发现后校验版本满足 `package.json#engines` 当前要求。找不到兼容版本时不修改程序或数据，显示 Node.js 22 LTS 安装说明。完整首次安装包可以以后选择附带 `.runtime`，但 v3.1 更新包不强制捆绑 Node.js。

## 安全约束

- 只信任固定 GitHub 仓库的正式 Release。
- 所有路径在复制、删除或替换前解析为绝对路径，并验证仍位于应用根目录、临时目录或指定备份目录内。
- 更新包使用允许列表而非排除列表决定可覆盖内容。
- 下载体积、manifest 体积、解压文件数和解压总大小设置上限。
- 不在日志中打印 `.env.local` 内容、API Key、Cookie 或下载鉴权信息。
- 不使用 `Remove-Item` 对未经验证的计算路径执行递归删除。
- 不终止机器上的全部 Node.js 进程，只停止确认属于当前 OwnSpace 根目录的服务。

SHA-256 用于传输完整性和误包防护，不等同于代码签名。v3.1 不引入证书签名；这一限制在 README 中明确说明。

## 版本与界面

- `package.json` 版本更新为 `3.1.0`。
- 应用更新日志新增 `3.1`，介绍在线提示、离线升级和自动备份回滚。
- 启动提示与离线升级器使用简短中文文案；底层错误保留可诊断信息。
- README 增加首次安装、从旧版升级、GitHub 在线升级、离线升级、备份恢复和发布资源生成说明。

## 测试策略

PowerShell 测试以临时目录和假实现为主，不访问真实 GitHub，也不接触真实用户数据库：

- 语义化版本比较、manifest 校验和 Release 资产选择。
- Node.js 查找顺序和版本拒绝。
- ZIP 路径穿越、受保护路径、错误哈希和超限资源拒绝。
- 旧版目录中的数据、附件和 `.env.local` 在成功升级后保持不变。
- 强制模拟依赖、迁移、构建和健康检查失败，验证程序与数据库回滚。
- 在线检查失败、用户跳过时仍进入正常启动流程。
- 在线与离线入口最终调用同一升级引擎。
- 发布包不包含数据、密钥、Git 文件或缓存，manifest/hash 与实际 ZIP 一致。

最终验证包含 PowerShell 测试、TypeScript 类型检查、ESLint、现有测试集、生产构建，以及在临时副本上从 v2.3 数据升级到 v3.1 的一次端到端演练。

## 交付与兼容路径

v3.1 发布时同时生成完整分享包、在线更新资源和离线升级包。现有 v2.3 用户收到离线升级包后完成最后一次手动升级；该流程先备份旧数据并把 v3.1 升级器安装到原目录。之后每次双击启动器即可检查 GitHub Release。

开发工作区中目前未提交的飞书字段同步、DeepSeek 候选恢复和长期规划时间轴修改按用户授权与本设计文档一起纳入提交，不回退或拆除。
