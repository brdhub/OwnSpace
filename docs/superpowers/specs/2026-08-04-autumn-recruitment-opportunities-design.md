# OwnSpace 秋招投递企业库设计

日期：2026-08-04  
状态：已获用户确认，待实施计划

## 1. 目标

在现有“投递记录”模块中增加“秋招企业”入口，让用户从指定飞书多维表格手动同步当前开放的秋招企业，并完成两条最短路径：

1. 收藏企业：创建一条状态为“计划中”的本地投递记录。
2. 准备投递：打开现有投递记录表单，自动填充企业和岗位信息，用户确认后保存。

该功能继续遵守本地优先原则。飞书仅作为用户指定的只读外部来源，SQLite 仍是应用内唯一数据源。

## 2. 数据来源与边界

唯一允许同步的数据源为：

`https://qcn5ycyl8hgi.feishu.cn/base/DEVcbyxZHa0y1Os89MBcr0tNnjd?table=tblSgpBe77jUnejO&view=vewgPKxdon`

当前公开视图为“27届秋招”，可见字段至少包括：公司名称、批次、岗位更新时间、企业类型、行业、岗位、工作城市和不限专业。

约束如下：

- 只允许用户点击按钮后手动同步，不设置后台任务或定时抓取。
- 只读取上述固定 URL，不接受用户输入任意抓取地址。
- 不登录飞书、不写回飞书、不转载无关第三方内容。
- 同步失败时保留上一次成功同步的本地数据。
- 仅在一次完整同步成功后，将本次未出现的旧企业标记为不可用；不物理删除历史数据。
- 实施时同步更新 `项目工程约束.md`，将该 URL 登记为投递模块的唯一外部数据源例外。

## 3. 方案选择

采用“手动同步到本地 SQLite”方案。

没有选择页面每次打开都实时请求飞书，因为这会让核心页面依赖网络和第三方页面稳定性；也没有选择把企业名单静态写入代码，因为名单很快会过期。手动同步既能保持数据的新鲜度，也能让浏览、搜索、收藏和投递操作在同步后完全本地运行。

外部读取逻辑封装在投递模块内部，并通过固定来源常量、超时、响应大小限制和 Zod 校验建立边界。若飞书公开页面结构发生变化，界面显示清晰错误并继续使用旧数据。

## 4. 数据模型

新增 `recruitment_opportunities` 表，保存同步后的企业机会：

- `id`：本地主键。
- `source_record_id`：飞书记录稳定标识，唯一索引，用于幂等更新。
- `company`：公司名称。
- `batch`：招聘批次。
- `source_updated_date`：来源记录标注的岗位更新时间。
- `company_type`：企业类型。
- `industry`：行业。
- `roles`：来源中的岗位文本。
- `cities`：工作城市文本。
- `unrestricted_major`：是否不限专业。
- `application_url`：来源中存在且通过 URL 校验的投递链接，可为空。
- `is_active`：本次同步后是否仍开放。
- `synced_at`、`created_at`、`updated_at`：同步和审计时间。

在现有 `applications` 表增加可空的 `opportunity_id` 外键，指向 `recruitment_opportunities.id`，删除机会时设为 `null`。该关联用于防止同一企业机会被重复收藏，同时不影响已有投递记录。

所有结构变更通过 Drizzle migration 完成，不重建或覆盖用户数据库。

## 5. 同步流程

1. 用户在“秋招企业”页面点击“同步飞书”。
2. Server Action 校验固定来源标识，并调用投递模块内的只读同步适配器。
3. 适配器读取公开视图，提取受支持字段，并使用 Zod 校验每条记录。
4. 在数据库事务中按 `source_record_id` upsert；已有记录更新，新记录插入。
5. 只有完整读取成功时，才把本次未出现的旧记录设为 `is_active = false`。
6. 返回新增数、更新数和同步时间，刷新秋招企业页面。

解析器与网络读取分离。解析器使用固定样例进行单元测试，避免测试依赖真实网络。

## 6. 页面与交互

在投递模块增加 `/applications/opportunities` 页面，并在“投递记录”和“秋招企业”之间提供清晰的页内切换入口，不新增侧边栏顶级导航项。

页面顶部包含：

- 公司或岗位搜索。
- 企业类型、城市、不限专业筛选。
- “同步飞书”按钮。
- 最近成功同步时间及同步结果。

企业列表展示公司名称、批次、企业类型、行业、岗位、城市和来源更新时间。移动端改为纵向卡片，避免横向表格溢出。

每条企业记录末尾提供：

- **收藏**：通过 Server Action 幂等创建或更新关联投递记录，状态设为 `planned`，来源设为“飞书秋招企业库”，记录日期使用当天。已收藏时显示“已在计划中”，重复点击不产生新记录。
- **投递**：打开复用的 `ApplicationForm`，预填公司、岗位、来源、状态 `applied`、当天日期、投递链接及必要的来源备注；用户仍可编辑并确认保存。
- **打开投递页**：仅当来源提供有效投递链接时显示，使用新标签页打开，不替代本地记录确认步骤。

如果一条来源记录包含多个岗位，首版将岗位原文整体预填到表单，用户可在保存前缩减为实际投递岗位，避免未经依据拆分或猜测岗位。

## 7. 错误处理与一致性

- 所有写操作继续通过 Zod 校验的 Server Actions 执行。
- 收藏时以 `opportunity_id` 查询已有关联记录；存在则更新为“计划中”，不存在才新增。
- 投递表单保存后沿用现有成功提示和页面刷新逻辑。
- 外部响应为空、字段变化、超时或校验失败时，不清空本地企业库。
- 对外链只允许 `http:` 和 `https:`；页面文本按 React 默认转义显示。
- 不把外部页面 HTML 或无关内容保存到数据库。

## 8. 测试与验收

至少覆盖：

- 飞书样例记录可映射为本地机会字段。
- 无效记录和无效 URL 被安全处理。
- 重复同步不会创建重复机会。
- 同步失败不会停用或删除旧机会。
- 重复收藏同一机会不会产生重复投递记录。
- 收藏后的投递记录状态为“计划中”。
- “投递”表单正确预填公司、岗位、来源、状态、日期和链接。
- 搜索和筛选仅展示匹配且处于开放状态的记录。
- TypeScript、lint、自动化测试和生产构建通过。

## 9. 非目标

本阶段不实现：

- 后台定时同步。
- 向飞书写入收藏或投递状态。
- 自动替用户提交招聘网站表单。
- 岗位推荐算法或 AI 匹配排序。
- 多用户共享收藏与投递记录。
