# OwnSpace v3.4 修改文档：简历制作业务闭环

日期：2026-09-05
基线：当前 package.json 为 v3.3.0，下一版本暂定 v3.4.0。
状态：需求与设计提案，供下一阶段实现使用；本次仅新增文档，不修改代码、依赖、数据库或发布版本。

## 1. 版本目标与取舍

让用户从已有简历素材出发，针对一个岗位完成选材、描述优化、人工审阅、简历组装、保存版本和导出。成功标准是得到一份能够实际投递、可继续编辑的新简历。

本版优先节省开发时间和模型 Token：

- 不实现需求—证据矩阵，不建立相关表，不增加相关模型请求或占位页面。后续可独立加入，不能成为本版流程的前置条件。
- 保留现有高/中/低匹配与简短理由；AI 推荐和 AI 优化都可以跳过。
- JD 检测仅指本地输入检查，不包含招聘真实性核验或独立模型分析。
- 简历组装、排版、保存、导出使用程序完成，不再请求模型重写整份简历。
- 可以试接 LangGraph JS，但仅编排一个小型优化子流程，不阻塞业务闭环发布。
- 继续采用本地优先、单用户、模块化单体；不引入独立后端、Redis、消息队列、向量数据库或云日志。

现有项目/实习条目字段不覆盖所有成品信息。例如实习没有独立日期字段，个人联系方式也不属于正式条目。不能假设模型提取已经提供这些内容，本版在制作草稿中手动补齐。

## 4. 用户流程

```text
上传 PDF → 本地提取 → 可选 AI 提取 → 确认正式条目
                                      ↓
已有正式条目 ───────────────→ 创建岗位任务 / 从投递进入
                                      ↓
                            JD 本地检查与编辑
                                      ↓
                         手动选材 / 可选 AI 推荐
                                      ↓
                       保存选材 → 可选 AI 优化
                                      ↓
                      审阅建议 → 生成简历草稿
                                      ↓
                  补充基本信息 → 编辑、排序与预览
                                      ↓
                  保存版本 → DOCX / 打印另存 PDF
```

### 4.1 创建任务与 JD 检测

- 保留投递记录带入岗位和 JD 的现有入口；页面打开和历史恢复不触发 AI。
- 新增“保存岗位并选材”，无需配置 API Key，也无需先获得推荐结果。
- 目标岗位必填。手动制作允许 JD 为空；AI 推荐/岗位优化要求 JD 非空。相应调整现有 schema，避免服务端仍强制阻拦手动路径。
- JD 检查只校验空值、现有长度上限、清理首尾空白；非常短的描述给出非阻断提示，不声称可以判断 JD 真伪。
- 图片来源沿用已经可用的入口与确认流程，不新增来源抓取或 OCR 引擎；文本粘贴必须可以独立完成本版全部流程。

### 4.2 推荐与选材

- 无推荐结果也展示全部正式条目，支持勾选和保存；至少一条素材才能生成草稿。
- AI 推荐继续返回等级与理由，不增加岗位画像、分数、矩阵等输出。
- 推荐仅协助选材，不能覆盖已保存的用户选择。用户可主动应用推荐选择。
- 选材保存使用素材快照，后续修改正式条目不静默改变当前任务或版本。
- 页面未保存的选择明确提示；优化与制作必须使用已保存选择，不能忽略未保存变更直接运行。

### 4.3 条目优化与审阅

- 仅发送当前任务 JD、目标岗位和已选素材；不发送姓名、电话、邮箱、整份 PDF 或其他任务内容。
- 每次优化默认一轮模型调用；维持禁止新增数字、技术、职责和团队成果归属的提示及结构校验。
- 接受采用建议，忽略保留原文；支持撤销接受/忽略，恢复待处理。
- 待处理建议不阻塞制作，但界面明确说明将保留原文，不可静默采用。
- 不增加 LLM 评审。结构检查只能约束字段，不能保证描述事实真实，最终内容由用户审阅。
- 重新优化前提示将替换本任务当前建议；成功后原子替换，失败保留旧建议与审阅状态。已生成草稿及版本不受影响。
- 只有输入版本一致的建议才能参与新草稿组装；过期建议不可应用。

### 4.4 简历制作

- 新增“制作简历”工作区，默认一个简洁、单栏、中文 A4 模板。
- 页面提供基本信息与分区编辑、预览、保存草稿、保存版本、导出。采用明确保存按钮，未保存离开时提示。
- 基本信息包含姓名、电话、邮箱、目标岗位；链接、城市可选。姓名和至少一种有效联系方式是保存正式版本的必要项；草稿允许不完整。
- 分区包含教育、技能、项目、实习/工作、荣誉。默认按此顺序，支持上下移动分区和条目、隐藏和恢复条目；不开发拖拽编辑器。
- 条目正文按段落/换行渲染，提供纯文本编辑。显示中文字段标签，成品不展示 JSON 字段名、匹配等级或优化理由。
- 允许在草稿中补充展示名称、组织、角色、起止日期和链接。教育标题优先作为学校名称，实习标题优先作为组织名称；映射后仍可编辑，缺失字段留空，不由 AI 猜测。
- 补充内容只属于当前草稿，不反向覆盖正式条目库。需要长期复用时，用户仍从正式条目管理入口维护。
- 生成规则：原素材快照为底；已接受且未过期建议覆盖对应可优化字段；忽略、待处理和无建议条目保持原文。
- 已有草稿再次“生成”必须明确提示会替换当前草稿，允许取消；复制历史版本也使用同样规则。保存版本不自动重新生成内容。

### 4.5 版本与导出

- “保存版本”创建完整且不可变的内容快照，包含基本信息、条目正文、顺序、显隐状态、模板版本、岗位/JD 快照和来源标识。
- 草稿修改不改变历史版本；历史版本可查看、重导出、复制为新草稿。源条目或任务删除后，历史成品仍可访问。
- DOCX：使用 docx 库本地生成，提供可编辑文字、标准段落与超链接，不生成整页图片。
- PDF：本版按钮明确叫“打印 / 另存 PDF”，打开专用打印视图，由浏览器打印对话框保存；不宣称一键下载，也不将打开打印窗口标记为文件已保存。
- 默认导出已保存版本；有未保存草稿时，提示先保存版本或选择历史版本，不能悄悄导出旧内容。
- Word 与浏览器可能分页不同，不承诺像素一致。首版支持自然多页，不强行缩小字体或截断到一页。
- 打印视图隐藏导航、按钮等界面；适当保持标题与后续正文同页。超长条目允许跨页，不能溢出裁切。
- 不支持原 PDF 版式复刻、照片模板、自动翻译和模型自动压缩全文。

## 5. LangGraph 最小接入设计

### 5.1 方案比较与选择

| 方案 | 收益 | 代价 | 本版决定 |
| --- | --- | --- | --- |
| 复用现有调用 + 普通函数 | 最快交付闭环 | 无框架编排实践 | 可靠回退方案 |
| LangGraph JS 编排优化子流程 | 实践节点、状态和条件路由 | 新依赖及打包验证 | 首选试接范围 |
| 全流程图 + 持久 checkpoint + interrupt | 跨人工阶段恢复 | 重放、副作用和持久化适配复杂 | 后续 |

本版图结构：准备已选素材 → 生成建议 → 校验 → 成功结果 / 失败结果。结果返回后由业务服务在事务中保存，避免图重放直接重复写业务表。继续调用现有 DeepSeek 封装，不同时引入另一套模型 SDK。

图状态只包含 taskId、inputRevision、runId、材料快照、建议与错误等本次运行数据。人工审阅位于图运行结束之后，存储在 SQLite 业务表中。

本版不使用原生 interrupt 或依赖 MemorySaver 实现恢复。刷新后读取 SQLite 已保存结果；进程中断后的未完成 AI 调用由用户明确重试。应准确描述为“业务状态可恢复、AI 运行可重试”，不能宣传模型节点无缝断点续跑。

### 5.2 接入门槛和边界

- 试接投入上限建议半个开发日，属于排期上限而非工时承诺；超过上限仍有兼容/打包问题则采用普通函数发布闭环。
- 核对选定 LangGraph 版本与项目 Node、TypeScript、Zod 和 Next.js 服务端运行兼容性，锁定通过验证的版本。
- 图和调用仅运行在 Node 服务端，密钥与依赖不得进入客户端包。
- 成功、无效输出、超时路径与普通函数调用保持相同业务结果；不为了展示路由额外请求模型。
- 不接 LangSmith 云追踪，不引入外部编排服务，不创建多个“角色 Agent”。这个版本准确定位为 AI 工作流。
- 若正式引入，更新 package.json、lockfile、README 和工程约束中的本地编排说明；若撤回试接，应移除未使用依赖与示例。

## 6. 调用预算与失败策略

| 用户操作 | 常规模型请求数 |
| --- | --- |
| 上传/本地解析、JD 检查、手动选材 | 0 |
| 首次 AI 提取 | 1（沿用现有独立入口） |
| AI 推荐 | 1，可跳过 |
| AI 优化已选条目 | 1，可跳过 |
| 草稿编辑、组装、预览、保存、导出 | 0 |

已有正式素材的标准 AI 路径常规为两次请求；手动路径为零次。重试会增加请求，不能将此表解释为包含所有失败情形的绝对总量。

- 同一输入不因刷新、保存、预览或导出自动重新分析；用户主动“重新优化”才发起新的运行。
- 每次明确发起的操作最多两次 provider 请求，格式错误允许一次修复重试；图、SDK 和现有封装不能各自叠加重试。网络超时不自动重试，提示结果可能不确定，由用户选择重试。
- 不做模型自动分批、无限循环或后台重试。输入超过本次请求安全预算时提示减少选材，不静默截断经历；预算依据实际配置模型和接口上限验证后设为服务端常量。
- 双击提交用 runId 与服务端条件更新拦截；AI 请求期间不持有 SQLite 长事务。
- 一次运行绑定输入 revision，完成后只允许写回同一 revision。用户修改 JD/素材后，迟到结果不可覆盖新状态。
- 输入变化使旧推荐和建议失效；当前草稿与历史版本保持原样，用户可显式重新生成。
- 运行超时或进程重启后，超过本次请求时限加缓冲的 running 记录显示“已中断，可重试”，读取页面只修正本地状态，不再次请求 AI。重试产生新 runId，旧运行不能回写。

## 7. 数据调整

复用现有任务、素材和建议表，新增内容通过 Drizzle migration 演进；不删除数据库或要求重新提取所有历史条目。

| 对象 | 调整方案 |
| --- | --- |
| resumeOptimizationTasks | 增加 inputRevision，表达 JD/选材输入版本；不把现有 status=completed 当成整份简历已完成 |
| resumeOptimizationSuggestions | 记录 inputRevision，防止旧建议用于新素材；保持与素材的归属校验 |
| resumeDrafts（新增） | 每个任务一份当前草稿：taskId 唯一、contentJson、schemaVersion、revision、updatedAt |
| resumeVersions（已有） | 扩展名称、版本序号、schemaVersion、模板版本、保存幂等键；acceptedContentJson 存完整成品快照 |
| resumeAiRuns（新增） | runId、taskId、operation、inputRevision、输入摘要哈希、状态、起止时间、模型/提示词版本、错误类别；Token 用量可空 |

补充约定：

- 草稿 contentJson 使用统一且经过 Zod 校验的文档结构；编辑器、DOCX 与打印页共享同一内容模型，避免各自拼装。
- 保留条目/建议 ID 作为轻量来源信息即可，不建立句子级证据关系。
- 版本的 taskId 改为可空并采用删除置空，解除目前 onDelete=cascade 会连带删除成品的风险；完整任务背景在成品快照内保存。迁移保留全部旧行。
- 历史版本列表支持 taskId 为空的成品。已保存版本的内容和模板版本都不从现行素材动态读取。
- 旧版本 JSON 按旧结构读取并转换成查看模型；缺少联系方式时显示待补充，复制到草稿后可补齐，不伪造旧数据。迁移前读取真实旧结构，使用对应迁移样本测试。
- inputRevision 为旧任务填充确定默认值。无法证明与当前素材一致的旧建议标记需重新确认，不自动套入新草稿。
- 草稿保存采用 revision 条件更新，避免多标签页覆盖。版本创建使用唯一幂等键，双击不得产生两份版本；手动另存新版本产生新键。
- 日志只保存诊断元数据，不存密钥，不额外复制完整 JD、姓名或联系方式。未返回 Token 用量记为空，不能记作零消耗。

## 9. 实施顺序与验收

### 阶段 A：先做零 Token 闭环

手动任务与选材 → 草稿组装 → 编辑预览 → 保存版本 → DOCX 与打印另存 PDF。

验收：不配置 API Key，使用已有正式条目能够完成一份包含姓名、联系方式与经历的简历；刷新恢复草稿，重新打开版本可导出相同内容。

### 阶段 B：接上已有 AI 结果

推荐辅助选材 → 优化 → 审阅/撤销 → 按接受状态生成草稿 → 输入变更失效处理。

验收：接受、忽略、待处理分别使用正确内容；旧建议不套入新输入；重新优化失败不丢原建议；草稿修改不回写正式条目。

### 阶段 C：尝试 LangGraph 并完成发布验证

小型优化图、运行记录、请求预算、防重复及迟到回写校验；不满足接入门槛则保留普通函数编排。

最终验收清单：

1. PDF 上传、候选确认、投递带入 JD 等既有入口无回归；提取失败仍可手动建条目。
2. 无 JD/无 API Key 可完成手动制作；AI 入口正确校验缺少的输入与配置。
3. 无选材有清楚空状态；未保存、过期、失败状态不会误用旧结果。
4. 姓名与联系方式校验、显隐、排序、编辑均在预览与导出一致反映。
5. 草稿、正式条目、历史版本互不静默覆盖；源任务删除后历史版本仍可查看与导出。
6. 模拟双击、超时、运行中修改输入、多标签页保存，验证无重复版本及旧结果覆盖。
7. 一页和两页以上样例均检查 Word 与打印 PDF；检查中文字体、长链接、超长段落、空分区、分页与文字可复制，不允许内容截断。
8. 使用旧数据库副本执行 migration，验证条目、任务、建议、版本保留，备份恢复说明可执行。
9. 运行 npm run typecheck、npm run lint、受影响的 tsx --test 测试及 npm run build；新依赖进入发行包后再做本地启动和离线导出检查。
10. 模型调用主要使用模拟响应验证，最后用最少的手动样例检查实际服务；记录实际验证结果，不预先宣称通过。

## 10. 技术依据与设计边界

- [LangGraph persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence)：完整 checkpoint 恢复需要持久化配置；本版选择业务表恢复，暂不承诺图内恢复。
- [LangGraph interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts)：恢复会从中断节点开头重新执行，因此后续引入时必须处理重复副作用。本版人工审阅放在图外。
- [docx 官方文档](https://docx.js.org/)：提供 JavaScript/TypeScript DOCX 生成能力，具体依赖版本在实现阶段验证。

本版没有需求—证据矩阵并不影响闭环成立。产品价值由“已有素材能否低成本产出可投递简历”验收，LangGraph 作为有限的工程实践项，不增加用户必须等待的模型步骤。
