# OwnSpace 技术栈、中间件、通用方法与同类产品调研

更新时间：2026-07-08

## 1. 项目定位

OwnSpace 是一个本地优先的个人职业准备助手，面向准备后端开发、全栈开发和 AI Agent 相关实习的计算机专业研究生。它不是多用户 SaaS，也不是强提醒式打卡系统，而是一个安静、清晰、低压力的个人工作台。

当前核心模块包括：

- 首页 Dashboard 与每日最小行动。
- Applications 求职投递记录。
- Interviews 面经、问题和复盘记录。
- Journal 日记与每日状态记录。
- Study 学习打卡与学习资料记录。
- Planning 长期规划时间轴。
- AI Hub 常用 AI 工具快捷入口。

产品原则：

- 降低开始行动的阻力，而不是制造打卡压力。
- 优先展示少量真正有用的信息。
- 默认本地数据、单用户、无账号系统。
- 所有新增能力都应遵守 feature-first 目录边界。

## 2. 技术栈

### 2.1 运行时与框架

- Next.js 15.3.4：使用 App Router。
- React 19.0.0 / React DOM 19.0.0。
- TypeScript 5.8.3：项目启用严格类型检查。
- Node.js 运行本地开发、Drizzle migration 和 seed 脚本。

### 2.2 UI 与样式

- Tailwind CSS 3.4.17：负责页面布局、颜色、间距、响应式样式。
- shadcn/ui 风格的本地基础组件：`Button`、`Input`、`Select`、`Textarea`、`Badge`、`Card`、`Label` 等。
- Radix Slot：用于 `Button asChild` 等组合能力。
- class-variance-authority：用于基础 UI 组件 variant 管理。
- clsx 与 tailwind-merge：通过 `src/lib/utils.ts` 中的 `cn()` 合并条件 class。
- Lucide React：负责图标，例如导航、按钮、编辑、删除、缩放等。

### 2.3 数据层

- SQLite：唯一数据源，数据库文件位于 `data/ownspace.db`。
- better-sqlite3 12.11.1：本地 SQLite 驱动。
- Drizzle ORM 0.44.2：声明 schema、执行类型安全查询。
- drizzle-kit 0.31.1：生成与执行 migration。
- migration 文件位于 `drizzle/`，元数据位于 `drizzle/meta/`。

### 2.4 校验与服务端写入

- Zod 3.25.67：所有写操作的服务端输入校验。
- Next.js Server Actions：所有数据写入入口。
- `revalidatePath()`：写入成功后刷新相关页面数据。

### 2.5 工程命令

常用命令：

```bash
npm run dev
npm run db:generate
npm run db:migrate
npm run db:seed
npm run lint
npm run typecheck
```

Windows PowerShell 下推荐使用：

```powershell
npm.cmd run dev
npm.cmd run db:migrate
npm.cmd run db:seed
npm.cmd run lint
npm.cmd run typecheck
```

## 3. 中间件与基础设施说明

本项目当前没有使用传统意义上的 `middleware.ts`、独立后端中间件、认证中间件、Redis、消息队列或后台任务队列。

项目中的“中间层”主要体现在以下几个边界：

### 3.1 App Router 页面组合层

`src/app` 只负责路由、页面组合和 layout。例如：

- `src/app/page.tsx`：首页数据组合。
- `src/app/applications/page.tsx`：投递记录页。
- `src/app/interviews/page.tsx`：面经页。
- `src/app/journal/page.tsx`：日记页。
- `src/app/study/page.tsx`：学习页。
- `src/app/planning/page.tsx`：长期规划页。

页面文件应保持轻量，不承载复杂业务逻辑。

### 3.2 Feature 查询层

每个业务模块在 `src/features/<feature>/queries.ts` 中封装读操作。查询层负责：

- 从 Drizzle / SQLite 获取数据。
- 做必要的排序、筛选、聚合。
- 给 Server Component 或 Dashboard 卡片提供结构化数据。

示例：

- `applications/queries.ts`：投递列表、状态统计。
- `interviews/queries.ts`：面经筛选、问题标签等。
- `dashboard/queries.ts`：首页日程和今日行动。
- `planning/queries.ts`：长期规划节点和首页规划摘要。

### 3.3 Feature 写入层

每个业务模块在 `src/features/<feature>/actions.ts` 中封装 Server Actions。写入层负责：

1. 将 `FormData` 转成普通对象。
2. 使用 Zod schema 校验。
3. 写入 SQLite。
4. 调用 `revalidatePath()` 刷新相关页面。
5. 返回表单状态或静默完成。

通用结构：

```ts
const parsed = schema.safeParse(formDataToRecord(formData));
if (!parsed.success) {
  return { success: false, errors: parsed.error.flatten().fieldErrors };
}

await db.insert(table).values(...);
revalidatePath("/target");
return { success: true };
```

### 3.4 Zod Schema 层

每个 feature 使用 `schema.ts` 或 `schemas.ts` 定义输入结构。它负责：

- 必填字段。
- 字符串 trim。
- 最大长度。
- 日期格式。
- 枚举值。
- 可选字段预处理。
- 业务边界，例如 Planning 日期必须在 `2026-07-01` 到 `2027-06-30` 之间。

### 3.5 数据库 Schema 与 Migration 层

`src/db/schema.ts` 是 Drizzle schema 的单一声明位置。所有数据结构变更必须生成 migration，不允许通过删除数据库、静默重建或覆盖用户数据解决问题。

当前主要表包括：

- `applications`
- `daily_actions`
- `interview_notes`
- `interview_questions`
- `interview_tags`
- `interview_question_tags`
- `journal_entries`
- `study_checkins`
- `planning_events`

### 3.6 Seed 层

`scripts/seed.ts` 是幂等初始化脚本。它当前负责：

- 初始化面经技术标签。
- 在空数据情况下写入虚构投递和面经示例。
- 写入少量虚构日记示例。
- 初始化长期规划系统默认节点和少量虚构用户节点。

seed 原则：

- 可重复执行。
- 不覆盖用户已有数据。
- 默认数据必须完全虚构。
- 系统默认规划节点通过唯一键或 `where not exists` 去重。

## 4. 当前通用实现方法

### 4.1 Feature-first 组织方式

推荐每个业务模块保持以下结构：

```text
src/features/<feature>/
├─ actions.ts
├─ queries.ts
├─ schema.ts 或 schemas.ts
├─ constants.ts
├─ types.ts
├─ utils.ts
└─ components/
```

职责划分：

- `constants.ts`：状态枚举、显示文案、静态配置。
- `types.ts`：feature 内共享类型。
- `schema.ts`：表单和 Server Action 输入校验。
- `queries.ts`：读操作。
- `actions.ts`：写操作。
- `utils.ts`：feature 内可复用纯函数。
- `components/`：只放该 feature 的 UI 组件。

### 4.2 表单与 Server Action 方法

当前表单常用模式：

- Client Component 使用 `useActionState()`。
- Submit 按钮使用 `useFormStatus()` 显示 pending 状态。
- 字段错误通过统一的 `FieldError` 小组件展示。
- 保存成功后调用 `onDone()` 关闭弹窗或刷新局部状态。

适合继续抽象但暂不急于抽象的点：

- `FieldError` 在多个 form 中重复。
- `SubmitButton` 在多个 form 中重复。
- `formDataToRecord()` 在多个 actions 中重复。

后续如果重复继续增加，可以放到 `src/lib/form.ts`，但不要提前做大而全的 form framework。

### 4.3 本地日期处理方法

项目使用 `YYYY-MM-DD` 字符串保存日期，避免把纯日期和具体时间混在一起。

通用工具在 `src/lib/date.ts`：

- `formatDate()`
- `formatDateTime()`
- `toDateInputValue()`

Planning 模块在 `src/features/planning/utils.ts` 里使用 UTC 日粒度做时间轴计算，避免浏览器时区导致日期偏移。

核心方法：

- `dateToTimelinePosition()`：日期转 0 到 1 的相对位置。
- `timelinePositionToDate()`：点击位置转日期。
- `clampDateToPlanningRange()`：限制到规划周期内。
- `formatPlanningMonthLabel()`：月份刻度标签。
- `isEventInPlanningRange()`：判断日期是否在规划范围内。

### 4.4 时间轴交互方法

Planning 时间轴的当前做法：

- 固定周期：`2026-07-01` 到 `2027-06-30`。
- 月份刻度由 `getPlanningMonthTicks()` 生成。
- 每个节点根据日期比例定位到横线。
- 任务使用黄色系，进度使用绿色系。
- 点击节点打开编辑弹窗。
- 点击空白时间轴按坐标推算日期并新增节点。
- 鼠标在图区域内滚轮切换密度。
- 显示密度包括：极简、紧凑、标准、舒展、展开、细看。
- 过近节点在缩小时自动隐藏，任务优先保留，进度优先隐藏。
- 缩略图常驻显示，帮助在不同密度下保持全局位置感。

### 4.5 Dashboard 联动方法

Dashboard 不承载完整业务，只展示“下一步入口”和少量摘要。

当前做法：

- Applications：状态统计和快速新增。
- Interviews：面试日程概览。
- Journal：今日记录入口。
- Study：今日学习进度。
- Planning：下一项任务、最近进度、入口。

后续新增模块时，Dashboard 卡片应遵守：

- 只展示 1 到 3 个关键事实。
- 提供跳转入口。
- 不在 Dashboard 堆复杂图表或完整列表。

### 4.6 UI 设计方法

项目整体应保持：

- 安静、清晰、可靠。
- 留白充足。
- 桌面端优先，兼顾基本响应式。
- 文案具体、温和、不施压。
- 用按钮、选择框、弹窗、卡片等熟悉控件解决问题。
- 避免高压倒计时、失败提醒、重度游戏化。

## 5. 同类产品调研

本节调研的是公开可访问的求职追踪、职业准备和申请管理工具。OwnSpace 不需要照搬它们的商业化、云同步或 AI API 能力，但可以借鉴其中适合本地个人工具的交互方式。

### 5.1 Jobscan Job Tracker

参考链接：https://www.jobscan.co/job-tracker

公开页面展示的核心能力包括：

- 将求职申请、保存的职位和面试集中管理。
- 用类似看板的阶段表达申请进度，例如从已投递移动到已面试。
- 保存面试日程、会议链接、联系人、重要备注、待办任务等信息。
- 提供 Chrome extension，把常见招聘网站上的职位保存到 tracker。
- 在职位卡片中结合简历匹配或优化入口。

对 OwnSpace 的启发：

- Applications 可以增加更轻量的“阶段看板视图”，与现有列表视图并存。
- 面试时间、会议链接、联系人、备注可以在 Applications 和 Interviews 之间更顺滑地联动。
- 每条投递记录可以增加“下一步动作”字段，降低每天打开后不知道做什么的阻力。
- 简历匹配类能力可以先不接外部 AI/API，而是做本地手动清单：JD 关键词、项目匹配点、待补表达。

### 5.2 Simplify Copilot / Job Tracker

参考链接：https://simplify.jobs/copilot

公开页面展示的核心能力包括：

- 浏览器扩展帮助自动填写申请表。
- 根据职位描述优化简历和回答。
- 自动记录通过工具提交的申请到 dashboard。
- 将“申请效率”和“追踪记录”结合在一起。

对 OwnSpace 的启发：

- OwnSpace 当前不适合实现自动填表或网页自动抓取，这会超出项目边界。
- 可以先支持“手动快速录入模板”：常用渠道、岗位方向、城市、实习类型、厂型等默认值。
- 可以增加“投递后复盘模板”：投递原因、JD 关键词、简历对应项目、预计准备点。
- 如果未来做浏览器扩展，也应只保存用户主动确认的数据，避免自动抓取第三方内容。

### 5.3 表格 / Notion / Trello 类自定义 Tracker

许多求职者会用电子表格、Notion database 或 Trello board 管理投递。它们的优势是自由、可视化、低门槛；缺点是结构容易发散，面经、学习、长期规划之间缺少稳定联动。

对 OwnSpace 的启发：

- 保持结构化字段，避免完全自由文本导致后续无法统计。
- 增加 CSV 导入/导出，让用户不被工具锁住。
- 保留“备注”和“反思”自由文本，承接结构化字段无法表达的上下文。
- 适当提供看板、时间轴、日历三种视角，但底层仍使用同一份 SQLite 数据。

## 6. 可改进方向

### 6.1 Applications 投递记录

建议优先级：P1

可改进点：

- 增加看板视图：按状态列展示投递记录，保留当前列表视图。
- 增加“下一步动作”字段：例如补简历、准备笔试、等待反馈、发 follow-up。
- 增加联系人字段：HR、内推人、面试官、联系方式、备注。
- 增加会议链接字段：用于远程面试快速打开。
- 增加“岗位方向”字段：后端、全栈、AI Agent、平台工程、数据工程等。
- 增加“优先级”字段：高、中、低，帮助今天只看最重要的几条。

实现建议：

- 小步新增字段和 migration。
- 先在列表里展示，不急于做复杂拖拽。
- 看板状态更新仍走 Server Action。
- 不引入重型 DnD 依赖，先用状态下拉或轻量按钮完成阶段切换。

### 6.2 Interviews 面经模块

建议优先级：P1

可改进点：

- 增加面试准备清单：项目介绍、八股、算法、反问问题。
- 增加“面试后 10 分钟复盘”快速入口。
- 将面试问题按主题聚合，形成薄弱点视图。
- 为问题增加熟练度：不会、模糊、可讲清、可举例。
- 从 Applications 的面试时间自动突出当天或近 3 天面试。

实现建议：

- 优先复用现有 `interview_questions` 和 tags。
- 熟练度可以先作为 question 字段扩展，不急于设计复杂知识图谱。
- Dashboard 只展示最近面试和一条准备建议。

### 6.3 Study 学习模块

建议优先级：P2

可改进点：

- 增加学习主题库：算法、Java、MySQL、Redis、系统设计、Agent 工程等。
- 增加资料链接管理：标题、来源链接、标签、用户备注，遵守不抓取第三方内容的约束。
- 增加“从面试薄弱点生成学习待办”的手动关联。
- 增加按周回顾：本周完成了什么、下周只保留哪 1 到 3 个重点。

实现建议：

- 不做推荐算法。
- 不抓取资料正文。
- 使用本地 SQLite 保存用户自己整理的链接和备注。

### 6.4 Journal 日记模块

建议优先级：P2

可改进点：

- 增加周复盘页面：从日记、学习、投递、规划中汇总一周变化。
- 增加状态趋势：只做轻量统计，例如精力低/中/高的天数。
- 增加“明日最小行动”与 Dashboard 每日行动的联动。

实现建议：

- 避免情绪评分过度量化。
- 不做压力型连续打卡。
- 复盘文案保持温和。

### 6.5 Planning 长期规划模块

建议优先级：P1 / P2

当前模块已经具备基础功能。可继续改进：

- 增加按月份折叠的下方列表，辅助时间轴阅读。
- 增加节点与 Applications / Study / Journal 的轻量关联。
- 增加“本月重点”区域，只显示 1 到 3 个重点节点。
- 增加规划节点批量导入/导出。
- 增加键盘缩放：`+` / `-` 切换密度。
- 增加缩略图拖动视野，而不只是点击跳转。
- 增加隐藏节点的可展开列表，说明哪些节点因缩放暂时隐藏。

实现建议：

- 不做复杂甘特图。
- 不做多项目依赖关系。
- 不做高压倒计时。
- 继续使用原生 React + CSS 完成时间轴交互。

### 6.6 数据导入、导出与备份

建议优先级：P1

这是本地优先工具非常值得补的一块。

可添加功能：

- Applications CSV 导入/导出。
- Interviews Markdown 导出。
- Journal Markdown 导出。
- Planning JSON/CSV 导出。
- 一键导出 SQLite 数据库副本。
- README 中明确备份路径：`data/ownspace.db`。

实现建议：

- 导出优先，不急于复杂导入。
- 导入时必须预览和确认。
- 导入不应覆盖已有数据。

### 6.7 搜索与全局导航

建议优先级：P2

可添加功能：

- 全局搜索：公司、岗位、面试问题、日记、学习主题、规划节点。
- 最近访问记录。
- 快速跳转命令面板。

实现建议：

- 先用 SQLite LIKE 查询即可。
- 不引入全文搜索引擎。
- 命令面板可后续再做，不作为当前必需能力。

## 7. 建议的近期 Roadmap

### P1：让已有记录更容易转化成下一步行动

1. Applications 增加“下一步动作”和“优先级”。
2. Dashboard 增加“今天建议看这 1 条投递 / 1 个规划节点”。
3. Planning 增加隐藏节点列表和键盘缩放。
4. 增加基础导出：Applications CSV、Planning CSV。

### P2：增强复盘闭环

1. Interviews 增加面试后快速复盘模板。
2. Study 支持学习资料链接库。
3. Journal 增加周复盘页面。
4. 从面试问题 tags 汇总学习薄弱点。

### P3：增强输入效率，但保持边界

1. 投递记录快速录入模板。
2. 从剪贴板粘贴 JD 后，手动提取公司、岗位、链接等字段。
3. 可选浏览器扩展调研，但不自动抓取、不绕过用户确认。

## 8. 不建议近期实现的功能

根据项目工程约束，以下能力暂不建议实现：

- 登录、注册、账号系统。
- 云同步。
- 多用户协作。
- 支付功能。
- 外部 AI API。
- 自动抓取招聘网站或第三方面经内容。
- 推荐算法。
- 微服务、Redis、消息队列、后台任务队列。
- 复杂拖拽甘特图或完整项目管理系统。

## 9. 新功能开发检查清单

新增 feature 前建议逐项确认：

- 是否真的需要新数据表。
- 是否遵守 `src/features/<feature>` 自包含结构。
- 是否有 Zod 服务端校验。
- 是否使用 Server Action 写入。
- 是否有 migration。
- 是否不会覆盖用户数据。
- 是否有空状态。
- 是否有 Dashboard 最小联动，且不过度展示。
